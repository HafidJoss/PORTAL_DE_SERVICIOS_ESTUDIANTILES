# Decisiones arquitectónicas (ADR)

Decisiones de arquitectura, el driver que responde cada una, su justificación y el resultado adoptado.

| ID | Decisión arquitectónica | Driver relacionado | Justificación | Resultado |
|---|---|---|---|---|
| ADR-001 | Arquitectura N-Tier (multicapa) desacoplada, con tier de aplicación sin estado | DA01 - Picos de demanda; DA04 - Desacoplamiento | Separar la presentación web, la API de servicios y el motor relacional permite mantener y escalar cada parte por separado; una API sin estado permite agregar instancias sin cambiar código. | SPA servida por Nginx, API en Python 3.12+ con FastAPI (al menos 2 instancias) y PostgreSQL 16+; la cola, el worker y el almacenamiento de objetos se despliegan como servicios aparte (ver ADR-007). |
| ADR-002 | Almacenamiento seguro en Object Storage (MinIO/S3) con subida directa y URLs prefirmadas | DA02 - Privacidad y seguridad | Cumplir con la Ley N.º 29733 evitando la exposición pública de los probatorios de menores, sin cargar el disco ni el ancho de banda de la API durante las campañas de admisión. | Bucket privado con nombres UUID y cifrado AES-256 en reposo. Subida directa del navegador con POST prefirmado (límite de 5 MB y tipos permitidos en la política) y descarga con GET prefirmado de 15 minutos. El worker verifica el tipo real del archivo por su contenido. |
| ADR-003 | Procesamiento asíncrono de reportes y documentos (cola Redis + worker Python) | DA01 - Picos de demanda; DA06 - Reportes SIAGIE | Evitar que la compilación de libretas PDF y actas Excel para cientos de estudiantes bloquee las peticiones HTTP. Pre-generar los documentos al consolidar el periodo convierte el pico de descargas en lectura de archivos. | Redis exclusivo para la cola (persistente, sin evicción) y worker Python con WeasyPrint (PDF) y openpyxl (.xlsx). Al consolidar el periodo se encola un lote por sección. La entrega es id de trabajo, estado y URL prefirmada; los reintentos usan espera creciente y los trabajos fallidos van a una cola aparte. |
| ADR-004 | Control de acceso basado en roles (RBAC) con autenticación JWT | DA02 - Privacidad y seguridad; DA05 - Vista multi-hijo | Aislar los 5 roles del colegio (Administrador, Secretaría, Docente, Apoderado y Estudiante) y validar cada petición sin consultar un almacén de sesiones, lo que mantiene la API sin estado. | Token de acceso JWT firmado de vida corta más token de refresco rotativo. Middleware RBAC por rol y reglas de propiedad en los casos de uso: el apoderado solo ve a sus hijos y el docente solo sus cursos. |
| ADR-005 | Auditoría con triggers transaccionales en la base de datos | DA03 - Integridad y auditoría | Garantizar que toda modificación de notas o estados de trámite quede registrada en la misma transacción, sin depender solo del código de la aplicación. | Triggers en PostgreSQL que escriben en tablas de auditoría. Como el trigger solo ve la conexión del pool, la aplicación fija el usuario y la IP del usuario final en cada transacción (`SET LOCAL`). El rol de la aplicación no tiene UPDATE ni DELETE sobre esas tablas; el módulo de auditoría solo las consulta (ver ADR-008). |
| ADR-006 | Estrategia de lectura en pico: caché, consultas agregadas e índices | DA01 - Picos de demanda | El día de publicación de notas se repiten miles de lecturas casi idénticas; resolverlas desde memoria protege a PostgreSQL y permite cumplir AC01. | Caché cache-aside en un Redis exclusivo (LRU, sin persistencia): TTL de 30–60 s con invalidación al confirmar notas, TTL largo cuando el periodo está Consolidado, jitter y bloqueo contra estampida. Endpoint agregado por apoderado, pool de conexiones acotado por instancia e índices por (estudiante, periodo). La autorización se evalúa siempre antes de leer la caché. |
| ADR-007 | Despliegue en contenedores con alta disponibilidad básica | DA01 - Picos de demanda | Cumplir AC02 con la infraestructura de un MVP: dos instancias de la API evitan caídas por fallo de proceso y permiten desplegar sin corte; el respaldo cubre la pérdida del servidor. | Docker Compose con Nginx, al menos 2 contenedores de API con health checks, worker, PostgreSQL, 2 Redis y MinIO. Respaldo diario de PostgreSQL y del bucket, con restauración probada. Riesgo aceptado: servidor único. |
| ADR-008 | Monolito modular con Clean Architecture por módulo | DA04 - Desacoplamiento | Un solo despliegue reduce la complejidad operativa dentro de las 12 semanas, y los módulos con fronteras claras permiten cambiar reglas CNEB, catálogos o proveedores sin efectos en cadena (AC06). | Cinco módulos (identidad_acceso, academico, evaluacion, admision, auditoria) con fachada pública, un esquema PostgreSQL por módulo y eventos de dominio en proceso. En cada módulo: presentación → aplicación → dominio ← infraestructura. La API y el worker son puntos de entrada de la misma base de código. |

## Estado, alternativas y consecuencias

| ID | Estado | Alternativas descartadas | Consecuencias |
|---|---|---|---|
| ADR-001 | Aceptada (2026-10-09) | Microservicios (complejidad operativa fuera del plazo); serverless (el worker de PDF y el estado en BD no encajan); aplicación sin capas (acoplamiento). | (+) La API escala sin tocar código y cada capa se mantiene por separado. (−) Más componentes que desplegar y monitorear. |
| ADR-002 | Aceptada (2026-10-09) | Subir los archivos a través de la API (la satura en campañas de admisión); guardarlos en la BD (carga el motor transaccional); disco del servidor (viola RC05). | (+) La API no maneja bytes de archivos; el acceso es temporal y cifrado. (−) Exige un endpoint público de storage y un paso de confirmación de la subida. |
| ADR-003 | Aceptada (2026-10-09) | Generar en la petición (bloquea la API); proceso nocturno (sin respuesta a demanda); una sola instancia de Redis para caché y cola (la evicción podría borrar trabajos). | (+) Las descargas del pico son lecturas de archivos. (−) Los documentos llegan con retraso y hay que monitorear la cola y los trabajos fallidos. |
| ADR-004 | Aceptada (2026-10-09) | Sesión de servidor (exige un almacén compartido consultado en cada petición); OAuth con un servidor de identidad externo (sobredimensionado para el MVP). | (+) La API sin estado escala. (−) Un token no se revoca antes de expirar; se mitiga con vida corta y refresco rotativo. |
| ADR-005 | Aceptada (2026-10-09) | Auditar solo en el código de la aplicación (puede omitirse); event sourcing (sobredimensionado para el MVP). | (+) El registro es atómico con el dato. (−) Lógica en la BD que hay que versionar y probar; el no repudio criptográfico (hash encadenado) queda como evolución. |
| ADR-006 | Aceptada (2026-10-09) | Solo índices (no absorbe el pico); réplica de lectura (queda como evolución); caché HTTP en Nginx (no sirve con autorización por usuario). | (+) La BD solo recibe los fallos de caché. (−) Hay que cuidar la invalidación y los datos pueden estar desfasados hasta 60 s. |
| ADR-007 | Aceptada (2026-10-09) | Instancia única (cualquier caída es un corte y los despliegues cortan el servicio); Kubernetes (sobredimensionado para un MVP). | (+) Tolera la caída de un proceso y permite desplegar sin corte. (−) El servidor único sigue siendo punto único de falla (RTO de hasta 2 h). |
| ADR-008 | Aceptada (2026-10-09) | Microservicios; monolito en capas sin módulos (acoplamiento, riesgo para AC06); carpetas globales por capa (el dominio no se distingue). | (+) Un solo despliegue, fronteras claras y dominio probable sin infraestructura. (−) Exige disciplina para respetar las fronteras entre módulos. |
