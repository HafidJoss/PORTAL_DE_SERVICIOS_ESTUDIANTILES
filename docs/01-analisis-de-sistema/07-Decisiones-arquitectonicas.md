# Decisiones arquitectónicas (ADR)

Decisiones de arquitectura, el driver que responde cada una, su justificación y el resultado adoptado.

| ID | Decisión arquitectónica | Driver relacionado | Justificación | Resultado |
|---|---|---|---|---|
| ADR-001 | Arquitectura N-Tier desacoplada sobre servicios gestionados de Google Cloud, con tier de aplicación sin estado | DA01 - Picos de demanda; DA04 - Desacoplamiento | Separar la presentación web, la API y el motor relacional permite escalar cada parte por separado; los servicios gestionados permiten que una sola persona construya y opere el sistema. | SPA en React + TypeScript + Vite servida por Firebase Hosting, que redirige `/api/**` a la API en Python 3.12+ con FastAPI sobre Cloud Run; PostgreSQL 16+ en Cloud SQL. |
| ADR-002 | Almacenamiento privado en Cloud Storage con subida directa y URLs firmadas | DA02 - Privacidad y seguridad | Cumplir con la Ley N.º 29733 evitando la exposición pública de los probatorios de menores, sin cargar la API durante las campañas de admisión. | Bucket privado con nombres UUID y cifrado en reposo. Subida directa del navegador con política POST firmada (límite de 5 MB y tipos permitidos) y descarga con URL firmada de 15 minutos; la firma usa la cuenta de servicio vía IAM y el bucket tiene CORS. Una tarea verifica el tipo real del archivo por su contenido. |
| ADR-003 | Procesamiento asíncrono con Cloud Tasks | DA01 - Picos de demanda; DA06 - Reportes SIAGIE | Evitar que las libretas PDF y actas Excel masivas bloqueen las peticiones HTTP, sin mantener una cola ni un worker siempre encendidos. | Cloud Tasks invoca un segundo servicio Cloud Run (misma imagen, solo accesible con token OIDC) que genera PDF con WeasyPrint y .xlsx con openpyxl. Las tareas son idempotentes y se encolan después del commit. Al consolidar el periodo se encola un lote por sección. |
| ADR-004 | Autenticación propia y RBAC con verificación de pertenencia | DA02 - Privacidad y seguridad; DA05 - Vista multi-hijo | Muchos apoderados no usan correo, por lo que el usuario es el DNI; la API se mantiene sin estado. | Contraseña con argon2, JWT de vida corta en la cookie httpOnly `__session` (la única que Firebase Hosting reenvía) con protección CSRF y límite de intentos de inicio de sesión. RBAC de 5 roles y pertenencia centralizada en dependencias de FastAPI: el apoderado solo ve a sus hijos y el docente solo sus secciones. |
| ADR-005 | Auditoría append-only escrita desde la capa de negocio | DA03 - Integridad y auditoría | La capa de negocio conoce al usuario y la IP, y escribir en la misma transacción hace el registro atómico con el cambio. | El service registra cada modificación de notas y cambio de estado de trámite en la bitácora dentro de la transacción de la petición. El rol de la aplicación no tiene UPDATE ni DELETE sobre la bitácora; la IP se toma de `X-Forwarded-For`. |
| ADR-006 | Estrategia de lectura en pico sin caché en servidor | DA01 - Picos de demanda | El día de publicación de notas se repiten miles de lecturas casi idénticas que deben resolverse sin costo fijo adicional. | Tabla de notas consolidadas precalculada al cerrar el periodo, endpoint agregado por apoderado, índices por (estudiante, periodo) y caché del cliente con TanStack Query. Las respuestas de la API llevan `Cache-Control: private, no-store`. |
| ADR-007 | Despliegue gestionado optimizado (escenario B) | DA01 - Picos de demanda | Cumplir AC02 conservando backups y recuperación gestionados por Google, con el menor gasto fijo posible. | Cloud Run con mínimo 0 instancias (1 en cierre, publicación y admisión) y tope de instancias tal que instancias × pool de conexiones quede bajo el límite de Cloud SQL. Cloud SQL de 1 vCPU y ~4 GB con backups automáticos y recuperación a un punto en el tiempo. Secretos en Secret Manager y alerta de presupuesto. |
| ADR-008 | Monolito modular con arquitectura en capas estricta por módulo | DA04 - Desacoplamiento | Un solo despliegue reduce la complejidad operativa dentro de las 12 semanas, y las capas estrictas son fáciles de seguir y verificar para un desarrollador apoyado en agentes de IA. | Diez módulos; en cada uno: router → service → repository, más `core/` para infraestructura. Un módulo solo llama al service de otro y hay una transacción por petición. Contrato OpenAPI → cliente TypeScript generado con Orval. Dependencias verificadas con import-linter en el CI. |

## Estado, alternativas y consecuencias

| ID | Estado | Alternativas descartadas | Consecuencias |
|---|---|---|---|
| ADR-001 | Aceptada (2026-10-16) | Microservicios (inviable para 1 desarrollador); Nginx y Docker Compose en una VM propia (backups y escalado a cargo del desarrollador); Next.js (SSR innecesario detrás de login). | (+) La API escala sin tocar código y no hay servidores que administrar. (−) Dependencia de Google Cloud, mitigada con Docker. |
| ADR-002 | Aceptada (2026-10-16) | MinIO propio (un servicio más que operar); subir los archivos a través de la API (la satura en admisión); guardarlos en la BD. | (+) La API no maneja bytes de archivos; el acceso es temporal y cifrado. (−) Exige un paso de confirmación de la subida. |
| ADR-003 | Aceptada (2026-10-16) | Cola Redis o RabbitMQ con worker (servidor siempre encendido, incompatible con escalar a cero); generar en la petición (bloquea la API). | (+) Pago por uso y reintentos gestionados. (−) Los documentos llegan con retraso y las tareas deben tolerar reintentos. |
| ADR-004 | Aceptada (2026-10-16) | Firebase Auth (gira en torno al correo); solo RBAC (deja expuestos datos de otros menores). | (+) La API sin estado escala. (−) Un token no se revoca antes de expirar; se mitiga con vida corta. La recuperación de contraseña la hace Secretaría. |
| ADR-005 | Aceptada (2026-10-16) | Triggers en PostgreSQL (no conocen usuario ni IP); event sourcing (sobredimensionado). | (+) Registro atómico con el dato y con contexto completo. (−) Un endpoint nuevo debe recordar auditar; se cubre con pruebas. |
| ADR-006 | Aceptada (2026-10-16) | Redis (Memorystore) desde el inicio (cobra desde que se crea; se activará si la latencia supera el umbral de AC01); caché en el CDN (no sirve con autorización por usuario). | (+) Sin costo fijo adicional y sin datos desfasados. (−) Toda lectura llega a PostgreSQL; se valida con la prueba de carga de AC01. |
| ADR-007 | Aceptada (2026-10-16) | Escenario A, gestionado completo (mayor costo fijo); escenario C, una sola VM (backups y escalado manuales); Cloud SQL en alta disponibilidad (duplica el costo). | (+) Backups y escalado gestionados con gasto fijo medio-bajo. (−) Arranque en frío con 0 instancias y riesgo de agotar conexiones si no se ajusta el pool. |
| ADR-008 | Aceptada (2026-10-16) | Microservicios; MVC (no define dónde viven las reglas de negocio); Clean Architecture completa con puertos y adaptadores (demasiada ceremonia para 1 desarrollador). | (+) Un solo despliegue, reglas simples y verificables en el CI. (−) Exige disciplina para respetar las capas y las fronteras entre módulos. |
